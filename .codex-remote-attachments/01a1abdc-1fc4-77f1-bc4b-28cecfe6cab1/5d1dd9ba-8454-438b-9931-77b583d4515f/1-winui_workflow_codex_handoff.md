# WinUI 3: визуальные действия, workflow и контекст — handoff для Codex

> Составлено по обсуждению с пользователем 5 ноября 2026 года. Это **структурированная передача содержания беседы**, а не дословный экспорт всех реплик. Примеры API и кода — проектные предложения, не существующая реализация. **Не начинать реализацию без анализа текущего проекта и согласования объёма изменений.**

## 1. Исходная задача

Пользователь разрабатывает Windows-приложение на WinUI 3 с настраиваемыми меню. Рассматривалась возможность встраивать мини-редактор PowerShell-скриптов, передавать скриптам контекст приложения, использовать альтернативные движки (JavaScript/Jint, Roslyn C# Scripting, Lua, ClearScript) или запускать внешние скрипты.

После обсуждения пользователь уточнил ключевое требование:

> «В основном простые действия которые можно очень быстро настроить Буквально перетаскиванием и парой галочек».

Поэтому **главная цель — не IDE для скриптов, а быстрый визуальный конструктор действий**. Пользователю понравилась идея визуального workflow, но он отметил, что интерфейсы Kando и утилит Logitech бывают неудобны.

## 2. Принятые направления и открытые вопросы

### Приоритетные направления, поддержанные пользователем

- Drag & drop как основной способ настройки команды: EXE, ярлык, файл, папка, URL, `.ps1`.
- Минимальное число обязательных полей; умные значения по умолчанию; несколько галочек.
- Возможность объединять простые действия в **линейную последовательность**, переставляя их.
- Постепенное раскрытие сложности: одиночное действие → последовательность → условия / скрипты.
- Переменные контекста для подстановки в параметры действий.
- Добавить стандартные каталоги Windows и переменные окружения в модель контекста.

### Предложения, ещё не утверждённые как требования

- Встроенный JS через Jint; PowerShell и другие языки — как внешние процессы.
- Monaco Editor через WebView2 для продвинутого редактирования скриптов.
- Условия If/Else, переменные, переиспользование workflow, JSON-RPC.
- Полный каталог из 24 действий и конкретные этапы MVP.
- Способ получения выделенного текста из сторонних приложений.

## 3. UX-концепция: Progressive Workflow

Три уровня:

1. **Простое действие**: перетащил объект в пункт меню → команда готова.
2. **Последовательность**: добавил второе действие под первым; шаги выполняются сверху вниз.
3. **Расширенная логика**: раскрыл параметры, выбрал источник данных, добавил условие или внешний скрипт.

Редактор — **вертикальный список карточек шагов**, а не граф с соединительными линиями. При выборе шага раскрываются его параметры. Перестановка drag & drop, дополнительно кнопки вверх/вниз. Отдельная панель для настройки выбранного пункта меню. Кнопка «Дополнительно» скрывает редкие параметры.

### Примеры автоматического создания команд

| Что перетащили | Что предложить |
|---|---|
| `.exe` или ярлык | Запуск программы |
| Папку | Открытие папки |
| Файл | Открытие в приложении по умолчанию |
| `.ps1` | Запуск PowerShell с выбранными параметрами |
| URL | Открытие адреса |
| Несколько объектов | Группа команд или последовательность (предложить выбор) |

Для простых действий можно показывать декларативные настройки вместо исходного кода: «Запустить», «Открыть», «Копировать», «Нажать клавиши» и т. д.

## 4. Референсы: Kando, CopyQ, Logitech, Flow Launcher

- **Kando**: радиальное меню, последовательности Actions/Workflows, события выбора/наведения/открытия. Рассматривались действия запуска команды, открытия файла/URI, эмуляции клавиш, макросов, буфера обмена, фокуса окна, задержки, закрытия меню, перехода между меню, сообщений WebSocket/TCP. Список требует проверки по текущей версии документации перед точным копированием.
- **CopyQ**: встроенные JS-сценарии и внешние команды; полезна идея независимой команды, привязываемой к меню, хоткею или событию.
- **Logitech Smart Actions**: визуальные последовательности, но интерфейс не всегда достаточно быстрый для простых действий.
- **Flow Launcher / PowerToys Run**: более развитая модель внешних плагинов; не обязательно для MVP.

Вывод обсуждения: **не копировать тяжёлый workflow-конструктор**. Удобство быстрой настройки важнее максимальной выразительности.

## 6. Модель контекста

Контекст создаётся для **конкретного запуска workflow**. Часть значений — снимок на момент вызова меню, часть вычисляется по запросу; результаты шагов добавляются по мере выполнения.

```text
WorkflowContext
├── trigger
│   ├── type
│   └── timestamp
├── selection
│   ├── text?
│   ├── files[]
│   └── fileDirectory?
├── clipboard
│   ├── text?
│   └── files[]
├── window                 # исходное окно ДО открытия меню
│   ├── title?
│   ├── processName?
│   ├── processId?
│   └── processDirectory?
├── explorer
│   └── currentDirectory?
├── menu
│   ├── id
│   └── itemId
├── env                    # разрешённые переменные окружения
├── folders                # Windows Known Folders
├── app                    # каталоги приложения
├── vars                   # пользовательские переменные
└── steps                  # результаты шагов
```

Примеры ссылок: `{selection.text}`, `{clipboard.text}`, `{window.processName}`, `{vars.url}`, `{steps.download.output}`.

### Принципы

- Не передавать сценариям живые `Window`, `ViewModel`, `DispatcherQueue` и другие внутренние объекты.
- Предоставлять **ограниченные DTO / контракт API**, с версионированием (`apiVersion`).
- Различать **исходное окно** и текущее активное окно: иначе горячие клавиши могут попасть в меню вместо целевого приложения.
- Отсутствующие данные допустимы (`null` / unavailable), особенно `selection.text`, `explorer.currentDirectory`.
- Не требовать явного шага «задать переменную» для обычных сценариев: поле шага может непосредственно ссылаться на контекст.
- Не хранить все значения как строки: нужны хотя бы `String`, `Boolean`, `Number`, `FilePath`, `FileList`, `WindowRef`, `Json`.
- Предлагать совместимые переменные в UI по ожидаемому типу.

## 7. Стандартные каталоги Windows и переменные окружения

**Добавить обязательно, но разделить пространства имён:**

```text
env.PATH
env.TEMP
env.USERPROFILE

folders.desktop
folders.documents
folders.downloads
folders.pictures
folders.music
folders.videos
folders.appData
folders.localAppData
folders.programFiles
folders.windows

app.configDir
app.dataDir
app.scriptsDir
app.tempDir
app.installDir
```

Примеры: `{folders.downloads}`, `{folders.documents}\Projects\{vars.projectName}`.

- `Environment.GetFolderPath(Environment.SpecialFolder.…)` подходит для ряда стандартных папок.
- Для полного набора и корректной обработки перенаправленных папок (OneDrive, другой диск) использовать Windows Known Folder API (`SHGetKnownFolderPath`, `FOLDERID_*`). Не строить Downloads как `%USERPROFILE%\Downloads`.
- Вычислять значения лениво через `IContextValueProvider` или на момент запуска, а не сохранять абсолютные пути в конфигурации.
- Предусмотреть `CombinePath`/типизированные пути вместо ручного соединения строк.
- Не раскрывать весь `env` встроенным сценариям автоматически: там могут быть секреты. Использовать allowlist или явное разрешение.
- В UI показывать человекочитаемые имена («Загрузки», «Документы»), а в конфигурации — стабильные ключи.

## 8. Как пользователь выбирает значения параметров

Для каждого поля три режима:

1. **Контекст** — выбрать переменную из списка (`selection.text`, `folders.downloads` и т. п.).
2. **Вручную** — ввести константу.
3. **Шаблон** — комбинировать текст и переменные (`https://www.google.com/search?q={urlencode(selection.text)}`).

Подсказки и автодополнение переменных обязательнее встроенного редактора кода. Для аргументов процессов использовать `ProcessStartInfo.ArgumentList`, не конкатенировать командную строку без экранирования. Для URL — корректное кодирование значений.

## 9. Примеры workflow

### 9.1 Открыть выделенный текст как поисковый запрос

1. Прочитать `selection.text` (если доступно).
2. Проверить, что значение не пустое.
3. Открыть URL `https://www.google.com/search?q={urlencode(selection.text)}`.

### 9.2 Открыть выбранный файл в VS Code

- Исполнитель: `Code.exe` (разрешить выбор исполняемого файла).
- Аргумент: путь выбранного файла (`selection.files[0]` или отдельный типизированный селектор).
- Закрыть меню и корректно восстановить фокус, если нужно.

### 9.3 Последовательность управления окном

1. Закрыть меню.
2. Активировать целевое окно.
3. Отправить горячую клавишу `Ctrl+V`.

### 9.4 Преобразование текста

1. Получить текст из контекста.
2. `Trim`/изменить регистр.
3. Установить буфер обмена.
4. Показать уведомление (необязательно).

## 10. Скрипты: архитектурный компромисс

Первоначально рассматривались:

| Технология | Оценка для проекта |
|---|---|
| PowerShell | Хорошо для Windows-автоматизации; предпочтительно внешний процесс |
| Jint (JS на .NET) | Возможный встроенный исполнитель для коротких сценариев |
| ClearScript + V8 | Более сложная поставка и нативные зависимости |
| Roslyn C# Scripting | Для доверенных расширений; сложнее изоляция |
| Lua | Лёгкий движок, но ещё один язык для пользователей |
| Внешний процесс | Универсальный базовый механизм; PowerShell/Python/EXE |

**Рекомендация**: сначала внешние команды и декларативные шаги. Встроенный Jint — опционально позже. Не делать PowerShell-редактор центральным интерфейсом.

Для внешних скриптов можно использовать JSON через `stdin` и JSON-результат через `stdout`; ошибки через `stderr` и exit code. Для длительных двусторонних сценариев в будущем — JSON-RPC / named pipes.

Пример входа:

```json
{
  "apiVersion": 1,
  "trigger": "menu.click",
  "selection": {"text": "Hello World", "files": []},
  "window": {"title": "Notepad", "processName": "notepad.exe"},
  "menu": {"itemId": "custom-action-1"}
}
```

Пример ответа внешнего сценария (предлагаемый протокол):

```json
{"action":"clipboard.setText","text":"HELLO WORLD"}
```

Приложение валидирует результат и выполняет разрешённую операцию. Запуск процесса **не гарантирует изоляцию**, если он наследует права пользователя.

## 11. Предлагаемые интерфейсы .NET

Ниже только иллюстрация контрактов, не готовая реализация:

```csharp
public interface IWorkflowStepHandler
{
    string Type { get; }

    Task<StepResult> ExecuteAsync(
        WorkflowContext context,
        CancellationToken cancellationToken);
}

public sealed record StepResult(
    bool Success,
    object? Value,
    string? ErrorCode,
    string? ErrorMessage);
```

Разделить:

- `WorkflowDefinition` — сериализуемое описание шагов и их параметров.
- `WorkflowContext` — состояние одного выполнения.
- `IWorkflowStepHandler` — реализация конкретного действия.
- `IValueResolver` — константа / переменная / шаблон.
- `IContextValueProvider` — ленивое получение системных данных.
- `IWorkflowRunner` — последовательное выполнение, отмена, ошибки, тайм-аут.

В JSON-конфигурации шагов предусмотреть `type`, `schemaVersion`, настройки, опциональный `id`. Нужны миграции конфигурации при развитии приложения.

## 12. Ошибки, безопасность, диагностика

- Поведение шага при ошибке: `Stop` по умолчанию, `Continue` опционально, `Retry` позже.
- `CancellationToken`, общий тайм-аут, ограничение параллельных запусков.
- Проверка существования путей и программ, понятные ошибки с указанием номера шага.
- Возможность тестировать **отдельный шаг**, не запуская весь workflow.
- Не сохранять в логах чувствительное содержимое буфера обмена и переменных окружения по умолчанию.
- Опасные операции (скрипты, произвольные процессы, действия с файлами) требуют явного подтверждения/предупреждения.
- Нельзя считать Jint или ограниченный PowerShell-runspace полноценной границей безопасности.
- Получение выделенного текста из чужих программ требует исследования: UI Automation может не дать доступ; резервное `Ctrl+C` влияет на буфер обмена и фокус.
- Действия с клавиатурой должны учитывать восстановление фокуса после закрытия меню.

## 13. Рекомендуемый порядок реализации

**Фаза A — минимальная полезная вертикаль:**

1. Изучить существующую модель меню, drag & drop, конфигурацию, механизм запуска команд.
2. Спроектировать `ActionDefinition` / `WorkflowDefinition` и `WorkflowContext` с версионированием.
3. Реализовать 5–8 базовых обработчиков: запуск программы, открыть файл/папку/URL, горячая клавиша, буфер обмена, закрытие меню, задержка.
4. Поддержать `folders.*`, `app.*` и минимальный `env.*`.
5. Создать UI: drag & drop → тип действия → минимальные настройки.
6. Добавить последовательность шагов и их перестановку.

**Фаза B — контекст и удобство:**

7. Резолвер переменных, шаблонов и типизированных значений.
8. Подсказки переменных, превью подставленного значения.
9. Диагностика и тест отдельного шага.
10. Внешние PowerShell/EXE через структурированный протокол.

**Фаза C — по подтверждённому спросу:**

11. Условия, переменные, преобразования текста.
12. Работа с окнами и файлами.
13. Встроенный Jint и редактор Monaco (если действительно востребованы).
14. Вызов вложенных workflow, события и сложные интеграции.

## 14. Что Codex должен сделать в первую очередь

1. **Не писать код сразу**: изучить репозиторий и существующие UX/архитектурные ограничения.
2. Найти существующие сущности меню/команд, сериализацию, UI настройки, drag & drop и запуск процессов.
3. Предложить минимальную архитектуру, которая не ломает существующие настройки.
4. Составить короткий MVP-backlog с критериями приёмки и примерами пользовательских сценариев.
5. Отдельно выявить риски WinUI 3: фокус, UI Automation, безопасность запуска, жизненный цикл окна, async/cancellation.
6. Предложить прототип UX прежде чем реализовывать полный каталог шагов.

### Главный критерий успеха

**Пользователь может настроить большинство повседневных действий перетаскиванием и парой галочек за считанные секунды.** Скрипты — escape hatch, а не обязательный способ настройки.
